## 四、核心链路

### 4.1 浏览 → 加购

首页/系列/商品页从 Supabase 读数据生成 HTML；购物车存在浏览器 localStorage（zustand），不登录也能加购。商品页按属性匹配 SKU，价格与库存按 SKU 显示，加购数量受库存限制。

### 4.2 下单付款（以 Stripe 为例）

1. 顾客在 `/checkout` 填地址，选择 Stripe 或 PayPal。
2. 服务器**不相信浏览器价格**：按 SKU ID 重查数据库，校验上架、库存、优惠码、运费，用整数 pence/BigInt 重算总价。
3. 若页面展示价与服务器价不一致，返回 409，让顾客确认新价格。
4. `prepare_payment_checkout` 在一个事务里建订单、写明细、写支付快照、**扣减库存并记录预占**、占用优惠券次数。
5. 创建 Stripe Checkout Session 或 PayPal 订单（各带幂等键）。
6. 顾客跳转支付；成功后 Stripe webhook 或 PayPal capture 回调。
7. 服务器验证签名、订单号、金额、币种。
8. `complete_payment_checkout` 在同一事务里：记收据、恢复再扣库存、优惠券次数 +1、订单改为已付款、准备邮件内容。
9. 发顾客确认邮件 + 店主提醒；顾客进入 `/order-confirmed`，用 HttpOnly cookie 轮询订单状态，确认后才清空购物车。

### 4.3 库存预占与幂等

- 库存是两阶段：创建支付单时先扣，付款成功时在事务里"恢复再扣"，失败或取消则释放。
- 预占状态机：`active → capturing → consumed / released`，用行锁串行化"捕获 vs 取消"。
- 幂等分五层：`checkout_requests` 请求键（HMAC）、`payment_receipts` 主键、`completed_at` 守卫、Stripe/PayPal 幂等键、Resend 幂等键。
- 结果：同一笔支付重复通知不会重复扣库存、重复发邮件；两个人同时买最后一件不会超卖。

### 4.4 退款与对账

- 后台退款先锁订单，Stripe 用幂等键创建退款，记录 provider id 与状态，再 `finish_order_refund`（可选回补库存）。
- 外部退款（Stripe 后台操作）通过 webhook 记入 `payment_refunds`，按累计金额判断是否整单退完。
- 后台"支付恢复"页面可以查看未处理收据、滞留订单、未完成退款，并重放确认/对账。

### 4.5 发货与物流

后台标记发货 → 校验状态与旧单号 → 写物流轨迹 → 发发货邮件 → 前台 `/track-order` 用订单号 + 邮箱查 AfterShip；送达后写 `delivered_at`。

### 4.6 邮件、订阅与优惠券

- 所有邮件走同一个 Resend 通道并写 `email_log`（成功/失败 + provider id）。
- 订阅是双重确认：提交 → 限流 RPC → 验证邮件 → 点击后签发一次性 10% 欢迎券。
- 优惠券在结账时由服务器重新校验（启用、未过期、次数未满、满足最低金额），折扣金额以服务器计算为准。
- 后台可单封发送营销邮件，支持私有桶附件（签名上传、服务端复核大小）。

### 4.7 账户与 GDPR

- 登录支持邮箱密码与 Google；游客订单在邮箱确认后通过 `claim_guest_orders` 认领到账号。
- 订单详情按 `id + user_id` 双条件查询，查不到统一 404，响应 `private, no-store`。
- 删除客户：先预览阻断项（未发货的已付订单、24 小时内待付订单、支付凭证、进行中的预占），再在事务里删除账号、匿名化订单 PII、保留金额/支付 ID 供财务对账。

## 五、做得好的地方（建议保留）

1. **服务端权威计价**：浏览器报的价一律不算数，全部按数据库重算，金额用整数 pence/BigInt。
2. **库存两阶段 + 行锁**：先占后扣、事务内恢复再扣，不超卖、不重复扣。
3. **多层幂等**：请求键、收据主键、完成时间守卫、支付平台幂等键、邮件幂等键。
4. **后台鉴权纵深防御**：全路径中间件先删伪造身份头，再统一校验管理员邮箱；每个后台接口再自查一次，并有回归测试。
5. **SEO 做得细**：canonical、OG、ProductGroup/CollectionPage/BlogPosting/FAQPage 结构化数据、旧链接 301、空系列 noindex、动态 sitemap、Google Merchant feed。
6. **媒体上传校验**：命名空间白名单、4MB 上限、magic bytes 与声明 MIME 交叉验证、数据库写入失败会清理存储对象。
7. **Sentry 隐私**：`sendDefaultPii: false`，请求数据全关，四个钩子递归清洗 PII，并有大量测试。
8. **GDPR 删除是"匿名化"而非"删账"**：保留金额与支付 ID，符合财务留存要求。
9. **测试基线扎实**：39 个文件、313 个测试，PGlite 真跑 SQL，覆盖支付原子性、幂等、退款、鉴权、隐私。

## 六、风险清单

> 优先级按"对钱、对合规、对线上可用性的影响"排序，不按修复难度。

### P0 —— 建议本周处理

**1. 新代码没有提交，线上可能不是最新版本**
- 17 个已修改文件 + 6 个未跟踪的新模块/迁移，包括 `lib/sentry-dsn.js`、`lib/hand-frayed-colour-notes.js`、`admin/lib/email-attachments.js`、`admin/lib/email-attachment-storage.js`、`admin/lib/upload-email-attachments.js`、`supabase/migrations/2026-11-21-product-image-column-types.sql`。
- 风险：一次 `git commit -am` 会漏掉新文件，干净 clone / GitHub CI / Vercel 构建会因缺 import 失败；如果按 `DEPLOY.md` 的 Vercel Git 集成部署，线上运行的仍是最后一次 push 的提交，11-20 之后的邮件附件等功能并未上线。
- 行动：明确 `git add` 这 6 个新文件 + 17 个修改文件，跑测试后提交并 push；确认 Vercel 构建通过。

**2. 备份导出不完整，且没有恢复工具**
- `scripts/backup-export.mjs` 的固定表清单漏了 `payment_refunds`、`admin_audit_log`、`checkout_requests`。
- 后果：恢复后所有退款订单都没有退款凭证，后台"已退款但无记录"会全部报警；审计轨迹丢失。`BACKUP.md` 说 dry-run 能发现漏表，实际只遍历固定清单。
- 行动：补齐表清单；写一个最小恢复/导入脚本；至少做一次恢复演练。

**3. 营销合规：没有退订，也没有群发**
- 营销邮件没有退订链接、没有 `List-Unsubscribe` 头；`subscribers.status` 永远不会变成 `unsubscribed`（没有接口、没有后台操作）。
- 同时，隐私政策和欢迎弹窗都承诺"可随时退订"；后台 Compose 可以向任意客户邮箱单发，但**没有群发功能**，而旧架构文档却写着"营销 → 写邮件 群发"。订阅名单收集了却从未使用。
- 风险：英国 PECR/UK GDPR 合规风险；对顾客的承诺无法履行；订阅数据的最小化原则不成立。
- 行动：加退订路由 + 邮件页脚/头；后台加"标记退订"；要么实现群发（只对已确认订阅者），要么在文案和文档里明确"不群发"。

**4. 拒付/争议（chargeback / dispute）完全没有处理**
- Stripe webhook 对白名单外事件一律 200；PayPal webhook 只处理 capture/refund。`charge.dispute.*`、`CUSTOMER.DISPUTE.*` 没有任何分支。
- 后果：钱被划走，订单仍是已付款/已发货，没有通知，后台支付恢复也看不到。
- 行动：订阅争议事件，落库并提醒店主；在后台加"争议中"状态。

**5. GDPR 删除有两个覆盖洞**
- 只有订单的账号才会出现在客户列表；**零订单账号**在后台无法找到、无法删除。
- 订单按 `customer_email` 精确匹配清洗；如果账号 `user_id` 关联了订单但结账邮箱不同，该订单的姓名/地址/电话在"删除客户"后仍保留。大小写不同的邮箱也会造成部分清洗。
- 行动：客户列表改为并集（`customer_summary` + `user_profiles`）；删除计划同时按 `user_id` 取订单，并统一小写比较；补测试。

**6. 部署没有 CI 门禁，部署文档缺关键变量**
- Vercel 由 Git 集成直接部署，CI 没有 deploy job、没有 `vercel.json`；CI 的 build 步骤在缺少 `NEXT_PUBLIC_SUPABASE_URL` 时只打印提示并**判为通过**。
- `DEPLOY.md` 的 Vercel 环境变量漏了 `ADMIN_EMAILS`（没有它没人能进后台）、`RESEND_API_KEY`/`EMAIL_FROM`（没有它邮件发送报错）、Sentry 变量；还列了代码不读的 `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`。
- 行动：补齐文档；让 build 在缺关键变量时失败；把 Vercel 部署与 CI 结果关联（至少约定 CI 绿了才合并）。

### P1 —— 建议两周内处理（影响收入/安全）

**资金与库存**
- **未认证结账接口可刷库存**：`create-checkout-session` / `create-order` 无需登录，每次调用都会真实扣减 `stock_qty`，没有限流/验证码/机器人检查；攻击者可用无限新请求键把 SKU 刷到 0，让店铺显示售罄。建议加 IP/会话限流 + 一次性令牌 + 可疑行为告警。
- **过期预占没有定时释放**：只在"下一次有人结账"时顺带清理；低流量时最后一个库存可能被 PayPal 2 小时预占长期占住。建议加 cron/pg_cron 定时任务。
- **Stripe 退款 webhook 乱序会被静默丢弃**：付款完成前 `orders.payment_intent_id` 还是 `cs_...`，退款事件找不到订单就 `continue` 并返回 200，Stripe 不再重试。建议找不到订单时返回非 2xx 或落库待对账。
- **结账回复写入失败会卡单**：`boundReply=true` 在 `saveCheckoutReply` 之前设置，写库失败后既不释放预占，同请求键重试又一直 409，直到 45 分钟/2 小时超时。建议调整顺序并加失败释放。
- **设置接口无服务端校验**：一次坏写（空值、逗号、科学计数法）会让所有结账报"无法校验运费"。建议服务端白名单 + 数值校验。
- **优惠券到期少一天**：`<input type=date>` 存成当天 00:00 UTC，结账用 `>= now()`，标注"有效期至 12-31"的券在 12-31 零点就失效。建议存当天 23:59:59 或按日期比较。
- **部分退款在后台不可见**：订单详情不查 `refund_requests`/`payment_refunds`，也没有"已退金额"字段；后台只能发全额退款，部分退款要去 Stripe 后台做。建议订单详情展示退款明细，并支持指定金额。
- **退款回补库存不区分部分退款**：`finish_order_refund` 按整单数量回补，部分退款后手动"标记退款"会把全部库存加回去。

**安全与运维**
- **`admin_media_usage` 在 jsonb 图片列上会 500**：新迁移专门支持 jsonb，但这个函数仍按 `text[]` 写。建议同步改写并加测试。
- **Google Shopping feed 的 `g:id`/`g:mpn` 未清洗**：旧 SKU code 可能超过 50 字符或含空格/引号，Merchant Center 会拒绝该变体。JSON-LD 有 `structuredSku` 守卫，feed 没有。
- **管理端若干写接口无服务端校验/审计**：优惠码、站点图片、文章、维护删除都信任客户端；营销发送、订单备注、取消、优惠码变更没有审计记录。建议补白名单校验与 `recordAdminAction`。
- **邮件附件只验扩展名**：媒体上传有 magic bytes，附件没有；建议同样做内容嗅探。
- **没有健康检查/uptime 监控**：唯一可用性检查是每天一次的 Playwright，而且依赖 CI 的 checks 通过。建议加 `/api/health` + 外部合成监控。
- **没有 CSP，会话 cookie `httpOnly:false`**：一旦出现 XSS，后台会话可被读取。当前未发现可利用的 XSS 注入点（商品描述走 sanitize-html，文章按文本渲染），属于纵深防御缺口。
- **CI 用生产 admin 账号跑 E2E**：登录失败截图/追踪可能包含密码，且该账号是完整管理员。建议用只读测试账号 + 失败前清空密码。
- **测试架构脆弱**：多数路由测试是"读源码 → 正则删 import → `new Function` 执行"，导入路径错误、缺文件、配置加载错误都测不出来（未跟踪文件问题就属于这类）。建议关键路由改为真实导入。

**数据与 SEO**
- **商品页实际是动态渲染**：页面 `await searchParams` 只为读可选 `?sku=`，Next 16 因此把整页转为请求时渲染，`revalidate = 60` 不生效；每次访问和爬虫都重查商品、SKU、系列、设置、相关商品。建议把 `?sku=` 改成客户端读取，恢复 ISR。
- **细丝/木轴 family 映射只存在于一次性脚本**：`split-fine-silk-ribbons.sql` / `split-wooden-spools.sql` 不在迁移里，新环境/恢复环境无法重建，商品页和 feed 会 500 或回退空。建议写成迁移或种子。
- **sitemap 可能输出 404 系列 URL**：`products.collection` 是自由文本，sitemap 直接用它生成 URL，而系列页对未知 slug `notFound()`。建议与 `COLLECTION_SLUGS` 取交集。
- **空系列 `patterned-ribbons` 仍出现在全站导航/页脚**：首页、系列索引、sitemap 都已过滤，只有 `Navbar.jsx` 和 `Footer.jsx` 硬编码了六个系列。
- **政策页写错分析服务商**：`/cookies` 说是 Vercel Analytics，实际加载的是 GA4。
- **Cookie 同意无法撤回**：接受/拒绝后横幅不再出现，但政策页说"可随时用横幅管理"。
- **GA4 没有购买/开始结账事件**：只上报 `view_item` 和 `add_to_cart`，且 `/checkout`、`/order-confirmed` 被排除，永远看不到收入和转化。如果不是刻意隐私设计，应补 `begin_checkout`/`purchase`。

### P2 —— 一个月内（体验/SEO/可维护性）

- 商品没有任何可售 SKU 时，按钮永远显示"Please Select Options"，应显示"售罄/暂不可售"并 noindex。
- 系列页排序的"Featured"是空操作（查询没取 `is_featured`）。
- 系列页 hero 用 CSS `background: url()`，绕过 next/image，LCP 没有优化。
- 多数内容页继承首页的 OG 标题/URL，分享出去像首页。
- 欢迎弹窗的"已购买不再弹"标记没有任何代码写入；`?verified=` 时无条件 `replaceState('/')`。
- 首页所有数据库查询静默吞错，故障时返回"空店铺"而不是错误页。
- FAQ 运费文案用裸 `parseFloat`，坏值会显示 `£NaN`，且整数四舍五入与结账不一致。
- 搜索接口数据库故障返回 200 + 空数组，顾客以为"没有这个商品"。
- `lib/seo-meta.js` 驱动所有商品页 meta description，却没有测试。
- 订单状态在 `lib/order-status.js` 与 `admin/lib/status.js` 各定义一份，靠约定同步。
- 购物车小计用加购时的旧价格，改价后展示与实收可能不同（结账会纠正）。
- 账户页未检查 401，登录过期时显示"暂无订单"。
- 结账自动保存的地址标签硬编码中文"结账时保存"，英文前台直接显示。
- 退款/取消后再次打开 `/order-confirmed` 显示"订单未确认"。
- 批量打印超过约 1000 行明细会被 PostgREST 截断而不报错。
- 媒体删除忽略 Storage 删除失败，留下无法管理的孤儿文件。
- 图片压缩把透明 PNG/WebP 画到 canvas 上转 JPEG，透明区域变黑。
- 商品编辑器提示"价格为空也可以继续"，但接口拒绝空字符串。
- 订阅接口从不返回 `already`，"已订阅"分支不可达。
- 邮件记录筛选缺 `subscription_verification` / `welcome_coupon` 类型。
- 联系表单收件人硬编码 `song@onesilkribbon.com`，没走 `siteConfig.ownerEmail`。
- `database-bootstrap.test.cjs` 漏了 2026-11-08 两个后台迁移，干净数据库不会验证这些函数。
- 迁移顺序只靠 MANIFEST 文字，没有脚本校验"每个 .sql 恰好出现一次且顺序正确"。
- 没有 Dependabot/Renovate，GitHub Actions 未固定 SHA；没有 `npm test` 脚本。
- 没有 `SENTRY_AUTH_TOKEN` 文档，source map 可能没上传，堆栈是压缩后的。
- 根 `.gitignore` 没有排除客户数据导出（`*.xlsx`、`output/`、`.codex-remote-attachments/`），一次 `git add .` 可能把客户名单提交进去。
